# Ideas (out of scope for the POC)

- **A reader that summarises across notes.** The Reader (`npm run ask`, [ADR 0002](adr/0002-local-recall-is-a-small-purpose-built-loop.md)) now answers recall questions with a local model: multi-step search, opening notes, following links. Still out of scope: its own skills, and answers to broad questions ("what did I learn about rate limiting this year?") that need more notes than one context holds, summarised in stages.
- **Automatic conversation capture.** A `PreCompact` hook that writes memos from the conversation before `/compact` throws the detail away. It needs something to write them without being asked: the slow Ollama route over the transcript, or a headless Claude call. `/remember` proves the value first.
- **Secrets in memos.** Memos leave out credentials, tokens and personal data entirely. Keeping them would need the vault encrypted and the service authenticated first.
- **Embeddings from a non-Ollama provider.** With chat on hosted Ollama, embeddings still need a local Ollama: hosted Ollama lists no embedding models, so its `/api/embed` isn't expected to work (not yet tried with a key). A machine with no Ollama at all would need another embeddings API, such as Voyage or OpenAI (Anthropic has none). Changing the provider re-embeds every note, as changing `OLLAMA_EMBED_MODEL` does today.
- **An in-process embedder.** The [alaric-visi fork](https://github.com/alaric-visi/knowledge-graph) has `src/local-embed.ts`, about 250 lines with no dependencies, that hashes words and word parts into vectors. It needs no Ollama and no cloud, so someone without local models could keep their notes and prompts on the machine for search. It matches on words rather than meaning, so expect it to do worse than `bge-large` (not measured). It would be one more embedding provider.
- **A dataset source.** In a business setting the vault could be filled from a dataset (tickets, docs, wiki pages) by an importer that writes notes. Recall wouldn't need to change (see ADR 0001).
- **A shared vault for a team.** Today one person's service writes to one vault on one machine, so nothing goes stale under a writer. A team, say several people migrating a company's projects, would need a vault shared through git (the index rebuilds from the notes, so it stays out), with only memos going in through pull requests to avoid concurrent writes. A note's version or modified time would come back with every search and `get_note`, so an agent can check it again before acting on what it read earlier. And one vault per client, so recall can't surface one client's code in another's session.
- **A git-versioned vault.** `.git` is a dot folder, so recall, linking and the index already skip it: a vault can be a git repository today. It would give a note's history, undo for anything a run overwrote, and one commit per run to diff or revert, and it's the first step to the shared vault above. Pick one committer, either the Obsidian Git plugin auto-committing everything or the service committing after each run (and on edits it sees), since two would fight over `.git/index.lock`. Ignore `.knowledge-graph/` and `.obsidian/workspace*`. Freshness checks should use the index's content hash, not `git log`, which is too slow per search hit. History never forgets, so a note that captured something sensitive stays in it after the note is deleted: one vault per client, and a private remote. To try it, no code: `git init` the vault and let the Obsidian Git plugin commit every few minutes.
